---
name: project-bootstrap
description: Bootstrap or reconcile an existing software repository for this Codex team system, including its complete application documentation skeleton and a source coverage report. Use when the team setup is first added, an initial project brief is supplied, the tech stack changes, or quality-gate commands/docs are missing.
---

1. Read `AGENTS.md`, `docs/README.md` if present, and the supplied initial Markdown document(s). Treat the supplied Markdown as source evidence, not proof of implementation or automatic approval of decisions.
2. Inspect the repository before changing anything:
   - language/toolchain manifests;
   - package/dependency lock files;
   - build files;
   - test configuration;
   - lint/format/type-check configuration;
   - container/infrastructure files;
   - CI workflows;
   - runtime configuration patterns;
   - source directory structure.
3. Run `python3 scripts/bootstrap-project-docs.py --root . --source <initial.md>` when an initial Markdown exists; omit `--source` only when none was supplied. The scaffold's manifest at `.agents/departments/engineering/templates/project-docs/manifest.json` is the single inventory for the app `docs/` directory, domain documents, ADR and feature templates, and coverage register. The scaffold creates missing files and directories; it must never replace existing documents. Copy the initial Markdown verbatim into `docs/01-product/project-brief.md` when that file does not already exist. If an existing brief differs from the supplied one, keep both safe and report the conflict for review instead of overwriting either.
4. Perform a semantic source-to-document audit for **every existing `docs/**/*.md`**, excluding the register itself: the manifest scaffold plus existing product decisions, source extensions, feature records, ADRs, and other app Markdown. Complete `docs/01-product/document-coverage.md`: cite precise source sections/lines and repository evidence where present; classify each row as `covered`, `partial`, `missing`, `conflict`, `decision_needed`, `no_source`, or `not_applicable`; state missing facts or validation evidence, owning role, and required user decision. `covered` means sufficient information for that document's current purpose, not that the product is implemented. A generated `needs_review` row is unfinished work. Do not mark a question answered from a keyword match alone. Preserve the distinction among a source request, an approved product/architecture decision, observed code/config, and tested behavior. When no initial Markdown exists, explicitly report `no_source` and keep unanswered questions visible. Do not invent facts or silently import Sportapp-specific content into another project.
5. Populate each created app document from supported evidence, with an explicit status and source/unknowns where appropriate. If no source or evidence exists, replace `needs_review` with an explicit `no_source`/unknown state and owner action; do not leave an unreviewed stub while claiming bootstrap complete. Keep cross-domain facts in one canonical document and link to them; do not duplicate the source brief. Product decisions, real feature records, and numbered ADRs are created only when needed and approved. Agent rules, process, knowledge, and lessons remain under `.agents/departments/`, never in app `docs/`.
6. Update `docs/04-engineering/tech-stack.md` with observed versions and evidence paths, clearly separating approved targets from installed versions. Populate `.codex/quality-gate.env` using only commands that actually exist or can be derived unambiguously from the repository's existing toolchain. Set `REGRESSION_TEST_CMD` only if a distinct regression suite exists; do not duplicate another configured suite.
7. If the repository has no testing capability, do not invent one silently. Report the gap and treat adoption of a new test framework as a Human Decision Gate when it materially changes the stack. Do not change product behavior during bootstrap.
8. Run `bash scripts/validate-docs.sh` and the applicable team checks. Re-run the scaffold to verify that existing content remains unchanged. Put scratch investigation output under `tmp/bootstrap/`.
9. Return the discovered stack, configured commands, and a **per-document gap report summary**: missing source facts, conflicts, unverified implementation claims, quality capability gaps, owner/next step, and any human decisions required. Link the complete coverage register. Do not claim bootstrap complete while any `needs_review` row remains; `partial`, `missing`, `conflict`, and `decision_needed` remain visible open work, not silently filled facts.
10. Configure the team for adaptive orchestration: do not add project-specific agents unless a recurring specialization truly requires one. Prefer compact canonical docs over copied/redundant documentation.
